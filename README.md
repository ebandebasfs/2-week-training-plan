# Queue Booking

A slot-booking system: `api.queue-booking` (NestJS + TypeORM + SQL Server)
and `app.queue-booking` (Next.js + TanStack Query). Built over the 2-week
training plan in `ethanpatrickbandebas-training-plan.html` — Day 1 scaffold
through Day 9's transaction-safe booking endpoint.

## How to run

Prereqs: Node, a SQL Server instance reachable from your machine (the plan
used a real instance throughout, not SQLite/in-memory).

**API** (`api.queue-booking/`)

```bash
cp .env.sample .env      # fill in DATABASE_URL, PORT, CORS_ORIGIN
npm install
npm run migration:run    # applies src/db/migrations/*.ts in order
npm run seed              # optional: seeds 10 customers, 15 slots, 8 bookings
npm run start:dev
```

**App** (`app.queue-booking/`)

```bash
cp .env.sample .env.local   # NEXT_PUBLIC_API_URL, NEXT_PUBLIC_DEMO_CUSTOMER_ID
npm install
npm run dev
```

**Concurrency proof** (Day 9): `npm run proof:concurrency` inside
`api.queue-booking` — fires two concurrent `POST /bookings` for the same
slot and expects exactly one `201` and one `409`.

Other scripts of note (`api.queue-booking/package.json`):
`migration:generate` / `migration:revert`, `backfill:booking-status`,
`bench:index-seed` / `bench:index-teardown` (Day 6 index-timing benchmark,
fully reversible, never touches seed data).

## Data model

Three entities, all extending `BaseEntitySchema` (`uuid` PK via
`NEWSEQUENTIALID()`, `created_at`/`updated_at`):

- **`customers`** — `first_name`, `last_name`, `email` (unique), `username`,
  `password`. `1 → many` with `bookings`.
- **`slots`** — `capacity`, `appointment_date`, `start_time`, `end_time`,
  `is_available` (default `true`). `1 → 1` with `bookings`.
- **`bookings`** — `customer_id` (FK, indexed as `idx_bookings_customer_id`),
  `slot_id` (FK, unique index `REL_409d5b76fb2b0501a8c72dd4ee` — this is
  what makes the relation one-to-one and is the second line of defense
  against double-booking, see below), `status` (`pending` | `confirmed` |
  `cancelled`, DB `CHECK` constraint), `notes` (nullable), and
  `booking_status` — a Day 6 migration-drill column, deliberately separate
  from `status`, not wired into app logic.

`Slot.booking` and `Booking.slot` are the same `OneToOne` relation from
both sides; a slot either has no booking or exactly one.

## Double-booking design

`POST /bookings` (`bookings.service.ts`) closes the double-booking race with
two independent layers, both required — either alone has a gap:

1. **Row lock inside a transaction.** `UnitOfWork.run()` wraps the whole
   operation in `DataSource.transaction()`. Inside it, the target slot is
   read with `lock: { mode: 'pessimistic_write' }` (`WITH (UPDLOCK,
   ROWLOCK)` on the mssql driver) *before* its `isAvailable` flag is
   checked. A second concurrent request for the same slot blocks on the
   lock until the first transaction commits or rolls back, so it can never
   read "available" out from under the first request. This is the fix for
   the naive check-then-act version, which had a window between the read
   and the write where two requests could both see `isAvailable: true`.
2. **Unique index as the safety net.** `bookings.slot_id`'s unique index
   (generated by the `OneToOne` relation, not added separately) means even
   if the lock were somehow bypassed, a second insert for the same slot
   fails at the DB level. The service catches SQL Server error 2627/2601
   (unique-violation) and maps it to `409 Conflict` instead of a raw `500`.

Proved with real concurrency, not a sequential-await test: two
`POST /bookings` for the same slot fired via `Promise.all()` against the
live API + SQL Server, 4/4 runs came back exactly one `201` + one `409`
(`api.queue-booking/src/db/day9-concurrency-proof.ts`, full output in
`deliverables/day9/files/concurrency-proof.md`).

## Migrations

`api.queue-booking/src/db/migrations/`, run in order via `migration:run`
(`synchronize: false` — schema changes only ever happen through migrations,
never entity-driven auto-sync):

1. `InitSchema` — `customers`, `slots`, `bookings` tables, FKs, the
   `customer_id` index, and the unique `slot_id` index.
2. `AddBookingStatusCheck` — `CHECK ([status] IN ('pending', 'confirmed',
   'cancelled'))` on `bookings`.
3. `AddBookingStatusColumn` → 4. `BookingStatusNotNull` — the Day 6 drill:
   add `booking_status` nullable, backfill (`backfill:booking-status`),
   then a separate migration flips it `NOT NULL`. Three steps on purpose —
   adding a `NOT NULL` column directly on a populated table in one step
   either fails outright or table-locks while every existing row gets a
   default value written to it.
5. `RenameCustomerIdIndex` — renames the auto-generated index hash to
   `idx_bookings_customer_id` so scripts and docs can reference a stable
   name instead of a hash that regenerates if the relation ever changes.

Runbook with the full step-by-step + rollback verification:
`deliverables/day6/migration-runbook.md`.

## Known limitations

- **`UPDLOCK, ROWLOCK` instead of the plan's literal `UPDLOCK, HOLDLOCK`.**
  Functionally equivalent here because the lock is taken on a single row
  looked up by primary key — `HOLDLOCK`'s range/phantom-row protection
  doesn't apply to a single-row PK lookup. Would need revisiting if the
  booking flow ever locks a range (e.g. "any available slot in this
  window") instead of one known slot.
- **No composite `(slot_id, customer_id)` unique constraint.** Deliberate:
  a composite would still let two *different* customers double-book the
  same slot — the exact bug this design exists to prevent. The single-column
  unique index on `slot_id` is the correct safety net.
- **`booking_status` is a dead column.** Added for the Day 6 migration
  drill only; not read or written by any app code outside the backfill
  script. Don't confuse it with `status`, which is the real field.
- **No auth.** `app.queue-booking` uses a `NEXT_PUBLIC_DEMO_CUSTOMER_ID`
  env var in place of a logged-in session; `customers.password` exists in
  the schema but nothing hashes or checks it yet.
- **No cancellation/release flow.** Once a slot is booked there's no
  endpoint to cancel it and flip `is_available` back to `true` — `status`
  supports `cancelled` at the data level but nothing in the API sets it.
- **Index-timing benchmark numbers are seed-data-dependent.** The Day 6
  `customer_id` index showed no measurable difference at the 8-row seed
  scale and only paid off (70ms → 5ms) after bulk-seeding 200k rows;
  don't read the small-scale number as "the index doesn't matter."
